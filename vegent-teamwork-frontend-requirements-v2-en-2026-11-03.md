## 2. Core principles — these are requirements, not suggestions

1. **Team Work is core, not a plugin.** It lives in Vegent's main navigation and design system, with the same auth context as login/identity/member management (frontend-auth request v2.0). No separate app, portal, domain, iframe, or plugin panel.
2. **Login is optional; local work is default.** A user who is not signed in, has no backend configured, or cannot reach the backend must still be able to start Vegent, use local sessions, and run local tasks. Login exists only for Team Work. See §3.1 for the mandatory greyed-out / retry behaviour.
3. **Backend enforces; frontend reflects.** The backend is the security boundary for every permission. The frontend must reflect permissions accurately (including disabling an action with a reason where the user cannot use it), but must never be the only check. Where the backend returns a permission via a `capabilities` / `viewer` field (Project detail), the frontend must use that field — it must not hardcode a permission rule that contradicts it, and must list any contradiction as an open question.
4. **No backend change in this task unless the owner approves it.** If a requirement below needs a backend endpoint, field, or permission that the implemented backend does not provide, list it as an open question with evidence. Do not invent it, and do not change backend code to fit a frontend guess. This includes: no new GET imports endpoint, no new category-visibility rule, no new restore endpoint, no new media-type listing endpoint — unless GPT delivers them and this document is revised.
5. **Implementation scope:** implement in the Vegent frontend workspace. Do not deploy to a cloud environment, do not create cloud resources, and do not commit or push without the owner's explicit approval for that step. Local implementation and local verification are the scope of this task.
6. **Candidate status — do not overclaim.** The backend is a **local-verified candidate with AWS qualification pending**. No live S3, live provider, real Lambda benchmark, target RDS engine confirmation, or frontend end-to-end test exists in this delivery. The frontend must be built and verified against a local test backend (subject to the Gateway-event test-harness requirement in the auth request — public auth calls return 503 without a Gateway `aws.event`), and must state what it verified locally vs. what remains for owner qualification. It must never be presented to the team or to leadership as pilot proof.
7. **Feature flag is real.** `VEGENT_TEAMWORK_ENABLED` defaults to `false`; when off, every Team Work request returns 503 with code `TEAMWORK_NOT_ENABLED`. The frontend must distinguish flag-off/maintenance (code `TEAMWORK_NOT_ENABLED`) from transient 503s, must show "Team Work is not enabled on this backend" (not "upload failed, retry"), and must never treat flag-off as revocation, sign-out, or a data error. The same code-distinction rule applies to `STORAGE_NOT_CONFIGURED` (media allowlist or bucket/TTL missing) and `PROVIDER_NOT_CONFIGURED` (PR sync unavailable while mirrors stay readable).

### 3.1 Access and non-blocking behaviour

- **Backend contract:** 29 identity routes + 1 health route + 62 Team Work routes E02–E63 share one Lambda and one MySQL database. Reachability probe is `GET /api/health` (public; the delivered OpenAPI leaves its 200 body unspecified, so probe by HTTP status and do not parse health body fields as contract). When `VEGENT_TEAMWORK_ENABLED` is false, Team Work returns 503 `TEAMWORK_NOT_ENABLED` while identity stays available. No 429 exists on any Team Work route in the delivered OpenAPI (see §7.3).
- **Requirement:** When the backend login system is not deployed, not configured, or unreachable, the system defaults to local mode. Login and Team Work controls are shown as unavailable with an honest reason that distinguishes "not configured" from "unreachable" (for example, the backend is not set up yet vs. the network/VPN is not connected) and from "Team Work not enabled on this backend" (flag-off), and the user can retry without restarting Vegent.
- **Acceptance:** Vegent starts immediately without waiting for a backend reachability check. A user can create a local session, run a local task, view local history, and edit local Project Context while the backend is unavailable, and a local task in progress is never cancelled, paused, or errored by a failed backend call. A user who was signed in and then loses connectivity keeps their stored credentials, keeps local work, and sees Team actions as unavailable with a stale-data label — they are not signed out automatically and are not shown a login wall. A timeout (15-second Lambda candidate timeout, or a slow VPN call) is shown as transient/unreachable, never as revocation or session expiry.
- **What you decide:** how unavailable controls are presented in your design, and what the retry interaction is. The outcome above is fixed; the presentation is yours.

### 3.2 Projects, Categories, and SubProjects — three levels, inherited membership

- **Backend contract (as implemented):**
  - Hierarchy is exactly Category → Project → SubProject, max 3 levels, enforced at DB level (parent depth guard + depth CHECKs make child-of-child impossible; a child-of-child request returns 422). A Project is created with `{name, category_id, background, goals}` (E20); a SubProject with the same shape under a parent (E27). Standalone Projects have `category_id = "none"` in list filters.
  - Membership is inherited, not copied: a SubProject has **no** member endpoints of its own. Calling member operations on a SubProject id returns 409 `INHERITED_MEMBERSHIP` (carrying `current.members_href` per the delivered OpenAPI/feedback response; follow it wherever present); add/remove on a SubProject return 403 to non-creators.  The frontend must follow `members_href` where present and must use the parent's member list (Project detail `sections.members` is already rewritten to the root URL). Member routes use **project_member_id** (**ProjectMember** row id), never `user_id`, for remove (E04); add (E03) takes `body.user_id`; transfer (E05) takes `new_creator_user_id`. **SubProject member-op rule (delivery):** member operations on a SubProject return 409 `INHERITED_MEMBERSHIP` (with `current.members_href`); add/remove return 403 `FORBIDDEN` to non-creators. The reliable root link is `ProjectDetail.sections.members`, already rewritten to the root URL. The reliable root link is `ProjectDetail.sections.members`, already rewritten to the root URL. Passing a user id where a member id is expected returns 404 — but the API surface invites confusion, so the UI must label the two id domains sharply and must never let a user pick a member row id as if it were a user.
  - Root membership is bound to the current Team membership epoch: Team removal denies root and child immediately at read time (no tombstone list is ever sent); rejoin creates a new epoch and a new **ProjectMember** row on re-add (not a new Project row); old grants stay removed. A removed-then-rejoined member does not resurrect an old grant.

- **Requirement:** Team Work is a Team-internal workspace. ### 3.4 Project information — complete, in one place, via Context

- **Backend contract (as implemented):**
  - Project detail is E25 (`GET /api/teams/{team_id}/projects/{project_id}`), returning `ProjectDetail` with `background`, `goals`, `progress`, `counts`, `version`, `context_version`, `capabilities`, `viewer`, plus `team_name`, `scope`, `node_kind`, `parent`, `membership_source_project_id`, `creator`, `created_by`, `ownership`, and an embedded `subproject_page`. **Clarified:** `subprojects` is not a list — it is `SubprojectLink {count, href}`; `subproject_page` is a `Page[ProjectSummary] | null`, populated only for roots. `sections` in Project detail is a 9-key href map (tasks, prs, resources, comments, members, progress_history, decisions, open_questions, context), **not** the 10 Context sections — and `sections.members` is already rewritten to the root project's members URL (E25's `cursor/limit` drive **only** that embedded page and are silently ignored for a SubProject detail — do not pass them expecting a SubProject page).
  - **Context is the full shared record** (E11 manifest + section pages + E58 text fragments): 10 sections — `tasks`, `subprojects`, `members`, `prs`, `resources`, `decisions`, `open_questions`, `comments`, `progress_history`, `activity` — including comments, typed decisions/questions, node-specific child data, progress/activity, and logical resource references (never bucket/key/presigned URL). Context version is a hash over project content + eligible member set (in the delivery design §881 the digest also covers team id **and name**, parent id/name, root-shared status/category/creator/ownership/lifecycle/membership/ownership times, member ids + team-membership ids + user ids + display names + emails, counts, and child hashes — so a team rename, a member display-name/email change, a count change, a category/ownership change, or a child-version change all invalidate the version though no project content changed; the frontend must treat such a version change as "re-fetch", not as "content changed"). **Delivery consistency (gate REMOVED): the delivered OpenAPI, delivered design (§858), and delivered manifest all specify Context `schema_version "2.1-r3"` consistently — there is no r2/r3 mismatch inside this delivery, and E11 is buildable from it. (No live server run is included in the delivery; runtime behaviour is local-test evidence only.)**
  - **Long text is a TextRef, not a string** (mandatory): any field >2,048 chars is `{inline: null, ref: {kind, object_id, field, resource_version, context_version, utf8_bytes, href}}`, resolved via `GET …/context/text?kind&object_id&field` with `If-Match` = context version, character `offset` paging, per-fragment **cap** 131,072 chars — the delivered OpenAPI/contract state no numeric default for E58 `limit`, so the frontend must pass `limit` explicitly (e.g. 131072) rather than relying on an assumed default — plus `next_offset`/`complete`. **Selector rule (corrected):** `resource_version` is **required** for kind=resource and **forbidden** for every other kind (else 422 `INVALID_TEXT_SELECTOR`); unknown kind/field, negative offset, or `limit ≤ 0` → 422 `INVALID_TEXT_SELECTOR`; unknown object → 404 `NOT_FOUND`; `offset > length` → 422 `INVALID_OFFSET`; `offset == length` returns empty text with `complete: true`. A missing or malformed Context `If-Match` on a section fetch or E58 → 422 `INVALID_VERSION`, not 409. This applies to project background/goals, progress note, task description, PR title/branch, resource name, context-item context/body/answer, and progress-event notes. Any frontend rendering `background` as a string breaks on every large field. TextRef resolution must be a first-class frontend-contract section, not a footnote.
  - **Version conflicts:** entity version is a quoted integer `"123"` (stale → `VERSION_CONFLICT` 409, with a `current` payload whose shape varies: `{version}`, `{entity_version}`, a progress object (progress update), a full **ProjectDetail** (project update/lifecycle), a **Task** view (task patch/status/lifecycle), or a **Comment** view (comment edit/delete) — read it, do not assume one shape; `{members_href}` belongs to `INHERITED_MEMBERSHIP`, **not** to version conflicts); Context `If-Match` is a 64-hex context hash, quotes optional (stale → `CONTEXT_CHANGED` 409, with **no** `current` payload). Member add/remove/transfer use the **root project version** (members have no version field); resource archive/delete use **`entity_version`, not `version`** (the DTO's `version` is the S3 resource version). **Section-page If-Match is required; manifest If-Match is optional** (missing/malformed on a section/continuation fetch → 422 `INVALID_VERSION`). Ordering trap: `get_context` runs before the 304 check, so a simultaneously supplied mismatched `If-Match` yields `CONTEXT_CHANGED` before any 304. Never reuse one version value across endpoints.
  - **Import / Context manifest:** E11 returns a manifest (`schema_version`, `project`, `context_version`, `observed_at`, `sections`, `import_mode`) plus section cursors. `If-None-Match` (→ 304) works only on a manifest fetch with no section/cursor, else 422. First Context pages are capped at 3 items per section with cursors — a first page is never a complete import (see §3.6).
- **Requirement:** For a single Project, the user must be able to see and work with its complete information in one coherent place: background and task goals, task composition, creation time, progress, members, PR list for review, resources, recent activity, and comments (§3.5). The user must be able to create, update, and archive/delete Project information according to their role, and must be able to navigate back to the multi-Project view without losing their previous filter or position.
- **Acceptance:** A member can find each of those information types without hunting through unrelated screens, can tell what they can and cannot do from their role (creator vs. member, from `capabilities`/`viewer` where provided) and from the SubProject inheritance rule, and can perform the actions they are allowed to perform without encountering a dead flow. Editing Project information, task status, or progress must handle concurrent edits honestly: on `VERSION_CONFLICT` / `CONTEXT_CHANGED`, show current data and ask the user to re-apply — never silently overwrite, never lose the user's draft. On `CONTEXT_CHANGED` specifically: bounded retries (at most 3 restarts, per the design), then **preserve/pause the local draft** and tell the user to resume manually — never auto-retry in a loop, never discard the draft, never claim a partial Context is complete.
- **What you decide:** whether Project detail is a separate page, a panel, or another structure, and how its information is organised. The completeness and role clarity above are fixed; the structure is yours.

### 3.5 Comments — discussion inside the Project, as a foundation for future IM

- **Backend contract (as implemented):**
  - Comments are Project-level with optional attachment: `CommentCreate` is `{content, task_id?, pr_id?, resource_id?, parent_comment_id?}` — content only for mentions (no separate mentions array, `extra="forbid"`). Replies are **flat** (`parent_comment_id` references a comment, but there is no nested-thread model in the contract — do not render deep nesting as if the backend modelled it; show a flat list with a reply reference).
  - **Mention grammar (frozen, from the optimisation §7):** the user never types the wire format — a picker generates the canonical token `@[Display Name](user:<positive decimal user id>)`, display name 1–100 chars. Plain `@name` is ordinary text with **no** mention row. Escaped `\@[` is ordinary text. A malformed token (`@[Name](user:abc)`, or any non-matching `@[`) 422s the **whole** mutation with a safe message that does not echo input. Bounds: ≤10 distinct mentioned users, ≤20 occurrences, content 1–4,000 Unicode chars / ≤16,384 UTF-8 bytes after LF/NFC normalisation. Rendering must use the DTO `mentions` array's user id, never parse a display name. Edited comments show an "edited" label with edited time; revision diffs are not exposed. Deleted comments are tombstones (`is_deleted`, empty mentions, `"[deleted]"` label in some views) and remain in counts (see §3.3).
  - **Former-member rule (corrected — P1-1 segment rule does not exist in the delivery):** a former member's token may be *retained* on edit but never newly introduced, copied, or retargeted. Retention in the delivery is by **exact user-id/token-label occurrence budgets from the immediate prior version** (feedback response P1-1) — surrounding prose may change freely. What fails 422: newly introducing a former member's token, copying one beyond its prior count, changing its display-name text (identity includes the name), or exceeding ≤10 distinct / ≤20 occurrences. Frontend rule: on such a 422, preserve the user's draft verbatim and explain that a former member's mention cannot be newly added, copied, or renamed — never lose the comment on this error. (The segment-equality rule belonged to the superseded 2.1-r2 delivery; it is NOT delivery behaviour in 2.1-r3 — see Divergence log §7.6.) Also: mention DTO `name` is a **snapshot**, refreshed to the current canonical label only when the comment is next edited, so a rename with no comment edit leaves the DTO stale — the frontend must honour 'current canonical label' by joining the current member list by `user_id`, not by trusting the DTO name alone.
  - **Content policy (warn-only, narrow) — field list corrected:** covered fields are top-level `content, note, context, body, answer, background, goals, description, progress_note`, plus a recursive `payload` dict — **task descriptions DO get warnings** in the delivery (the old 'no warning on task descriptions' claim was wrong). Detector failure yields a `validator_unavailable` warning, never a 503 that loses input. Label it in the UI as "possible-secret hint (4 patterns only)", never as "secret detection" or DLP.
  - **Mentioned-me:** defined exactly as active `comment_mentions` + non-deleted comment + visible project. Tombstones remove public mention relations. A removed member cannot post new comments; their past comments remain as history.
  - **Who can do what:** any Project member can post; only the author can edit their own comment; **delete is creator OR author** (corrected — not creator-only); there is **no** `can_delete_comment` capability field, so this cannot be verified against `capabilities` at runtime — the code rule is the rule. Comment delete replays to 204 on same-key retry, as do all other deletes except project delete (see §7.4). Replies are **flat and enforced**: a reply's parent must be a comment in the same project, a parent that is itself a reply → 422 `INVALID_REPLY`, a deleted parent → 409 `COMMENT_DELETED`, more than one anchor (`task_id`/`pr_id`/`resource_id`) → 422 `INVALID_ANCHOR`, and a reply with a mismatched explicit anchor → 422 `INVALID_ANCHOR` — the backend *rejects* second-level replies, so the frontend must not render deep nesting.
- **Requirement:** Team Work does not support IM in this version, but members must be able to discuss a Project inside the Project itself, as part of the Project's complete information, and that discussion must be a foundation a future IM feature can build on — not a separate chat system bolted on later.
- **Acceptance:** Any Project member can post a comment on a Project, and can attach it to a task, PR, or resource where that makes sense (via `task_id`/`pr_id`/`resource_id`), so a clarification about a specific task or PR is not lost in a flat list. A member can @ mention another Project member via the picker, the mention is clearly visible and identifiable as a chip (not just plain text), a former member's chip is visibly distinct, and a mentioned member can find comments mentioning them. A user can tell who wrote a comment, when, in what Project role, and whether it was edited. Existing comments remain as Project history even after a member leaves; a removed member cannot post new comments. Comments are explicitly not real-time chat: no typing indicators, presence, or read receipts are promised in this version.
- **What you decide:** how comments are composed, displayed, grouped, and filtered. The capabilities and the @-mention behaviour above are fixed; the presentation is yours.

### 3.6 Local Projects vs. Team Work Projects, import, and conversion

- **Backend contract (as implemented):**
  - **Local vs. Team distinction is a frontend responsibility:** the backend has no "local project" endpoint. Local Projects live in Vegent's local Project Context model (refactor request); Team Projects live in the backend. The frontend must never mix them in a way that hides scope, and must never send local session transcripts, tool outputs, execution content, or Personal Agent memory to the backend — the backend has no endpoint that accepts them, and the design forbids automatic upload. If a local-to-Team flow needs a backend field that does not exist, list it as an open question.
  - **Import (E12):** `POST …/projects/{project_id}/imports` records `{receipt_id, project_id, local_import_id, context_version, imported_at}` after checking only `local_import_id` + `context_version` equality. **It proves nothing about completeness** (P1-2). There is no GET imports endpoint, no snapshot stored, no local path/device/session accepted. `summary().capabilities.can_import` is unconditionally `True`, and `IMPORT` is exempt from the archived/orphan gates that block `WRITE_WORK` — so a frontend that disables Import on archived/orphaned projects from `read_only_reason` would diverge from the backend. Import is read-only Context import: no background or two-way sync is promised; post-import local work is via ordinary local actions, and any later push-back is a separate ordinary API action, not a sync promise.
  - **Conversion (E13 create, E60 seal, E61 prepare, E62 cancel, E16 commit, E59 items, E15 item upload authorizations):** phases are `planning → sealed → preparing → ready → committed`, plus terminal `cancelled` (E62, not possible after commit; re-calling commit on a committed session idempotently returns the detail). E13/E59/E60/E61/E62/E16 all require the session version as If-Match. Subproject conversion requires `existing_parent_id` + parent `CREATE_SUBPROJECT` grant, exactly 1 node, no `parent_node_key`, no `category_id` on node items (else 422 `INHERITED_CATEGORY`). Prepare batches max 50 items in fixed rank order (root node, child nodes, members, tasks, resources), bump the session version per batch, and return `next_prepare_cursor` — which is a **constant seal-guard** (scope bound to `plan_digest`), not an advancing position: prepare always takes the next ≤50 unprepared items regardless of the cursor value (a supplied cursor is only scope/digest-validated), and **what advances per batch is the session version** (bumped on every prepare call, including zero-item calls; delivery design states batches of 50 — do not rely on the E61 `limit` query param to change batch size). There is no re-seal: E60 from any non-`planning` state fails `CONVERSION_STATE_CONFLICT`, so no reseal can invalidate old cursors; a sealed-epoch change blocks with `PLAN_MEMBERS_CHANGED` instead. Commit requires `ready` + every item prepared + every selected resource verified with `resource_id == prepared_object_id`, else `CONVERSION_NOT_READY` 409. Prepared nodes stay invisible until commit publishes the root — with a precision: the root and subproject-mode nodes have `published_at` NULL until commit, but **root-mode child nodes get `published_at` set during prepare**; they stay invisible anyway because list visibility gates on the **root's** `published_at` (and `require_project` denies unpublished roots). A missing selected resource never publishes. **Sealed-epoch block:** member/actor epochs are pinned at seal; remove/rejoin → `PLAN_MEMBERS_CHANGED` 409 at prepare/commit, with no re-seal path — the only recovery is cancel + restart. SubProject conversion requires an existing Team parent; converting a parent does not automatically convert SubProjects unless explicitly selected; no Team SubProject without a Team parent. Conversion staging follows the same direct-S3 model as resources (§3.8). **Expiry (delivery):** missing `VEGENT_TEAMWORK_CONVERSION_EXPIRY_SECONDS` fails conversion creation outright with 503 `STAGING_POLICY_REQUIRED` (non-integer or ≤0 → 503 `SERVICE_NOT_CONFIGURED`); `expires_at` is then always `now + seconds` and past-expiry sessions fail 409 `CONVERSION_EXPIRED` — no NULL-expiry conversion can be created through E13 in this delivery. Legacy NULL-expiry staging from an earlier delivery is quarantined for a reviewed operator age-policy sweep (feedback response P1-6/P1-7), not silently accepted. The frontend shows creation 503 `STAGING_POLICY_REQUIRED` as "conversion not configured" (not a generic failure); a legacy no-expiry row, if ever seen, must be treated as quarantined/operator-handled, not as "expires soon".
- **Requirement (import):** A Team member must be able to bring a Team Work Project into their own local session scope and start working immediately — for example, to write code or to review a PR — with the Project's shared information available in that local session.
- **Requirement (convert):** A personal Project owner must be able to turn a personal Project into a Team Work Project, choosing the Team, the Category (or no Category), and the initial members.
- **Acceptance (both):**
  - **Shared / not-shared boundary (fixed):** Shared: Project Context only — background and task goals, task composition, creation time, progress, resource references, and the other Project information in §3.4. Not shared: session transcripts, tool outputs, execution content, and any other member's private local data. On import, the local session starts with Project Context, not with another member's chat history. On conversion, local files the owner selects as shared resources are made available through the backend (S3 via the backend service); local file paths themselves are not shared as-is. After import, the local work remains usable locally even if the user later loses Team Project access, while Team sync and Team access become unavailable. After conversion, the Project is visible in Team Work with its members, and the owner can say what happened to the original local Project.
  - **Import completeness (mandatory):** before recording a receipt, the frontend must traverse **all 10 Context sections + all TextRefs** for the recorded `context_version`, with cursors looped to `has_more: false` per section. It must store its own local-snapshot record against `local_import_id`: `{local_import_id, project_id, context_version, sections_fetched: [10 section names], textrefs_resolved: count, fetched_at, local_session_ref}`. It must be able to detect divergence later (re-fetch the manifest and compare `context_version`; a changed version means "Team Context has changed — re-import to update", not a silent merge), and "import again" must use a **new** `local_import_id`, not reuse the old receipt. A receipt recorded after only first pages is a failed acceptance — the verification checklist (§5) must include a large-Context import test (more than 3 items in at least one section, at least one TextRef field) proving full traversal.
  - **Conversion loop (mandatory):** loop prepare with a fresh version per batch (the cursor is a constant seal-guard, not a position) until `ready`, then commit; never show prepared content before commit; on `PLAN_MEMBERS_CHANGED`, show "Team membership changed since sealing — this conversion cannot continue; cancel and start again" with the user's selected files preserved locally for a restart (never lost). On `CONVERSION_NOT_READY`, show which gate failed (not ready / item unprepared / resource unverified) from the response, not a generic failure.
- **What you decide:** the import and conversion flows, the confirmation copy (which must state clearly what is shared and what is not, so the user is not surprised), and how the local Project relates to the Team Project afterwards. The shared / not-shared boundary above is fixed; the flow is yours.

### 3.7 Member management — creator-only, and consistent with identity

- **Backend contract (as implemented):**
  - Project member endpoints are E02 list, E03 add (`{user_id}`), E04 remove (path `project_member_id`, **no body**), E05 ownership-transfer (`{new_creator_user_id}`). Member view is `{project_member_id, user_id, name, email, project_role, joined_at, added_by, membership_status}`. There is no member version field — member mutations use the **root project version**.
  - **Creator-only rule (owner rule, verify at runtime):** only the Project creator manages a Project's members. Team Admins do not manage another person's Project members by virtue of Team role alone. If `capabilities`/`viewer` at runtime contradicts this (for example, a Team Admin action succeeding where the design says creator-only), list it as an open question with the route and response — do not silently broaden the rule in the UI.
  - **Identity consistency (epoch-bound cascade, I01):** Team removal cascades to Project memberships atomically (non-committing helper inside the identity removal transaction — verified). Read-time joins deny stale grants immediately, so a removed member's next request fails even before any reconcile sweep. **Flag-off gap (P0-8):** when `VEGENT_TEAMWORK_ENABLED=false`, the cascade is silently skipped and stale `status="active"` Project rows accumulate — but re-enablement without reconcile is **not** merely a hazard: `require_team` fails every Team Work call with 503 `TEAMWORK_RECONCILIATION_REQUIRED` while any stale active `ProjectMember` row exists. Repair is the operator script `scripts/teamwork_reconcile.py` (batches of 50 by `after_id`, requires provenance — removal audit or `user_deactivated` record — and raises if it is missing); there is no automatic sweep on re-enablement. The frontend must surface `TEAMWORK_RECONCILIATION_REQUIRED` as "Team Work needs reconciliation — contact an admin" (not a generic failure). The frontend must not assume that re-enablement alone cleans state — if Team Work was ever disabled, the verification checklist must include a reconcile confirmation from the owner before trusting member lists.
  - **Former members:** a removed member disappears from the roster, from @-mention candidates, and from `Mentioned-me` (tombstones remove public mention relations), but their past tasks remain with `assignee_membership_status = "former_member"` + `requires_reassignment = true` **unless the task is done** (`requires_reassignment` is false for done tasks with a former-member assignee; `assignee_membership_status` is `null` when there is no assignee) (the UI must show "needs reassignment" for non-done tasks, not a silently empty assignee), and their past comments remain as history with tombstone handling (§3.5). Re-adding a removed member is only via a new invitation / new Project add (new row, new epoch) — there is no reactivation route.
  - **Tasks:** task view includes `driver`, `assignee`, `assignee_membership_status`, `requires_reassignment`, `comment_count`, `comments_href`. Task states are exactly `todo`, `in_progress`, `blocked`, `done` (four states, no other value). Task create is `{title, description, assignee_user_id?}` (title/description required; driver is set to the actor, not the assignee); patch is **PUT** E34 `{title?, description?, driver_user_id?, assignee_user_id?}` (empty patch → 422; explicitly-null `driver_user_id`/`description` on patch → 422); status is a separate endpoint (E35 `{status}`). Permissions: patch = creator **or driver** (assignee alone → 403); status = creator, driver **or assignee**; archive/unarchive = creator or driver; delete = **creator only**; patch/status on an archived task → 409 `TASK_ARCHIVED`. Project patch splits similarly: name/category changes are creator-only, but `background`/`goals` may be patched by any member. Archive/unarchive are E36/E37 (`{}` body). Delete is E38 (`{"confirm": true}`).
- **Requirement:** Only the Project creator manages a Project's members. The member list a user can choose from is the Team roster: after a Team Admin invites someone into the Team, all Team members can discover each other, and any member can add other Team members to a Project they created. Project membership is not the same as Team membership, and Team Admins do not manage another person's Project members by virtue of Team role alone.
- **Acceptance:** A non-creator member can see who is in the Project but cannot add or remove members, and understands why (the rule is stated, not a generic "no permission"). A creator can add a Team member, remove a Project member, and transfer ownership (E05, to an already-eligible member only — the UI must not offer transfer to a non-member; a Team Admin viewer can also transfer an **orphaned** Project via E05). **There is no Project member-history endpoint** — member history is reconstructible only from activity events (E57/E63, e.g. `project_member_added/removed`) and, for Teams, the identity `GET /members/history` (Team-scoped, not Project-scoped); the acceptance criterion 'see member history' must be read that way, not as a dedicated endpoint. If a user is deleted from the Team, they disappear from the Team roster, from Project member lists, and from @-mention candidates, and they lose access to Projects in that Team — while their past tasks, comments, and history remain as history (the frontend must not show stale members from a local cache as if they were still members; on any 403/404 for a member list, re-fetch and invalidate the cache, never keep showing the stale roster). A SubProject's member list is the parent's list, with the inheritance rule stated — never a separately editable roster.

### 3.8 Resources, PRs, and progress — complete information, honestly sourced

- **Backend contract (as implemented):**
  - **Resources (E43 list, E44 upload authorizations, E45 upload status, E46 part authorizations, E47 complete, E48 cancel, E49 archive, E50 unarchive, E51 delete `{"confirm": true}`, E52 versions, E17 download authorizations):** file bytes go to S3, metadata to MySQL. The frontend obtains files **only** through the backend service, after a permission check, and must never expose a bucket name, a permanent S3 URL, or a raw S3 key to the user, and must never upload directly to S3 with a long-lived credential. S3 keys as implemented are `{prefix}/uploads/{uuid4}` (not team/project-scoped — prefix-wide IAM is the boundary, so the owner must confirm the prefix is deployment-dedicated; the frontend must not display a key as if it encoded team/project).
  - **Upload transport (mandatory, or large uploads fail mysteriously):** mode selection: `< 100 MiB` → single PUT regardless of SHA256; `100 MiB – 5 GiB` → single PUT *with* a declared SHA256, multipart *without* one; `> 5 GiB` → multipart is forced, so a declared SHA256 there is rejected with `CHECKSUM_MODE_UNSUPPORTED` 422 (the blanket 'multipart with SHA → 422' holds only for the >5 GiB case). Single PUT ≤5 GiB; part >5 GiB or part number >10,000 → `STORAGE_LIMIT_EXCEEDED` 422; non-final part <5 MiB at verify → `UPLOAD_CONFLICT` 409; No 5 TiB product cap is imposed in the delivery (design P2-2 rebuttal, citing current S3 limits: 10,000 parts × 5 GiB ≈ 48.8 TiB declaration boundary; single PUT is bounded at 5 GiB) — do not show 5 TiB as a limit; part-authorization pages are 1 MiB-capped with a cursor bound to the part-descriptor digest, and each part-auth call bumps the upload version (track the current upload version across steps; stale → `VERSION_CONFLICT` 409). Upload phases are authorize → parts → complete with `phase=verify` until verification is complete (multipart only — single-PUT has no verify/authorize phases; `phase != "confirm"` for a single-PUT upload → 422 `INVALID_PHASE`; `manifest_cursor` on any phase other than `authorize` → 422 `INVALID_PHASE`) → `phase=authorize` (traverse every manifest page, retain its common manifest hash) → send the returned signed POST directly with its required conditional headers → `phase=confirm` (Lambda HEAD-verifies version/checksum/length/type and publishes metadata once). **Do not ask Lambda to assemble multipart data.** Inspect the entire S3 body even after HTTP 200. After an S3 completion 409, follow S3 restart semantics with a new upload intent/client UUID, not an unconditional overwrite. S3 client timeouts are 1 s connect / 3 s read, single attempt (part `checksum_sha256` is schema-required, lowercase hex per part; duplicate part numbers in one call → 422; changing an already-declared part's size/checksum → 409 `UPLOAD_CONFLICT`) — transient S3 failures surface as `STORAGE_UNAVAILABLE` 503 mid-flow.
  - **Download + P0-1 warning (mandatory):** E17 authorizes a download and returns `DownloadAuthorization {resource_id, version, request: {url, method, headers, expires_at}}` — the bearer presigned URL is `request.url`, never a bucket/key. **`Resource.download_ref` is a different object:** `{resource_id, version, href}` where `href` is the **E17 endpoint path**, not a presigned URL and not a bucket/key — never present `download_ref.href` as the download link. The bearer URL is not bound to the actor, it can be forwarded, and it **survives membership loss, archive, and delete until TTL expiry** (TTL is owner-configured and returned as `expires_at` inside each `SignedRequest` — download `request.expires_at`, single-PUT `single_put.request.expires_at`, each part `request.expires_at`, complete-POST `request.expires_at`; the top-level `UploadAuthorization.expires_at` is the upload row's staging expiry, not the URL TTL. The delivery code ceiling is **900 s** (manifest `capability_ttl_ceiling_seconds: 900`); the owner TTL value is unselected in the delivery, so the frontend must read the per-request `expires_at` and never assume a maximum. Re-authorization mints a fresh TTL — replay does not pin the original URL). The frontend must: (a) never display, copy-link, or share the URL as a permanent link; (b) fetch through it immediately and discard it; (c) never claim that removing a member, archiving, or deleting a Project revokes an already-issued download; (d) show, on download, a short honest note for sensitive resources (for example, "This download link is valid until [expiry] even if access changes — do not forward it"). Pilot acceptance requires the owner to select and record a TTL value within the 900 s delivery ceiling (or proxy downloads, or rotate signing credentials) — the frontend must list the chosen mitigation in its design proposal and must not present the current bearer window as solved.
  - **Media allowlist:** `VEGENT_TEAMWORK_ALLOWED_MEDIA_TYPES` is required, non-empty, exact `type/subtype` strings, with **no default allow-all** and **no endpoint listing the configured types**. With it missing/empty, every presigning/mutating storage operation returns 503 `STORAGE_NOT_CONFIGURED` — the frontend must show "storage not configured" (not "upload failed, retry"), and must obtain the exact allowed list **out-of-band from the owner** with the qualified URL/stage. A type mismatch can otherwise only be learned by trial upload — the UI must not promise a type is allowed until the owner list confirms it. Pure metadata reads (E43 list, E45 get-upload, E52 versions) do not call `storage_config` and do not 503 on missing storage config.
  - **Upload/conversion expiry (delivery):** if the owner has not set `VEGENT_TEAMWORK_UPLOAD_EXPIRY_SECONDS` / `VEGENT_TEAMWORK_CONVERSION_EXPIRY_SECONDS`, creation fails outright with 503 `STAGING_POLICY_REQUIRED` (non-integer or ≤0 → 503 `SERVICE_NOT_CONFIGURED`) — no NULL-expiry row can be created through E44/E13 in this delivery; legacy NULL-expiry staging is quarantined for a reviewed operator sweep. The frontend must show pending uploads/conversions with no expiry as "no expiry configured — cancel explicitly if abandoned", and must list the owner's expiry values (or explicit no-expiry acceptance) as a handoff item in its proposal.
  - **PRs (E41 list, E42 sync):** the PR list is a mirror for review only. GitHub/Stash is the source of truth. The frontend must not offer to create, merge, or close a PR from Team Work, and must not offer a PR review action that writes to the provider. Sync is read-only, outside domain SQL locks, with a 3-second provider timeout, single attempt, no redirects, unapproved hosts denied. **Multi-page sync loop (mandatory):** sync returns `{state: running|completed, continuation, updated_prs, project_version}`; full listing is 100/page; explicit `external_pr_ids` sync is one PR per call; each page **with records** bumps the project version (`touch` runs only `if records:` — an empty-record page does not bump, so the next page's `If-Match` is the same version in that case), so the next page needs a **fresh Idempotency-Key and the fresh `project_version`** from the previous response in the normal non-empty case (same key → `IDEMPOTENCY_CONFLICT` 409). A failed page leaves page 1 mirrored with a fresh `synced_at` and **no partial marker** — the frontend must loop to `completed` and, if interrupted, show "sync possibly partial — retry sync to completion" rather than a clean synced state. If the provider secret is unset, sync returns 503 `PROVIDER_NOT_CONFIGURED` while stored mirrors stay readable (list requires only project READ) — the UI must show "PR sync unavailable — showing last mirrored data" (with `synced_at`), not "no PRs". Other provider failures are 503 (`PROVIDER_UNAVAILABLE`, `INVALID_PROVIDER_CONFIG`, `INVALID_PROVIDER_DATA`) except repository-scope problems → 422 `INVALID_REPOSITORY`. `repository_ref` values are keys into the owner secret, **not discoverable via API** — the owner must hand them to the frontend team out-of-band. Unmapped reviewers become `user_id: null`, `membership_status: external`, `reviewer_mapping_complete: false` (see §3.3 for the Dashboard undercount consequence). Mirrored reviewers never grant membership. Sync requires `WRITE_WORK` (archived → 409 `PROJECT_ARCHIVED`, orphaned → 409 `OWNERSHIP_REQUIRED`) — list (READ) stays available, but sync is not READ-gated. Reviewer-map entries for non-eligible users are **nulled to external at sync time** (not stored as reviewers, not a sync failure) — a mapped id that is non-integer or belongs to a non-member/former member becomes `user_id: null, membership_status: external, reviewer_mapping_complete: false`; the frontend must surface `reviewer_mapping_complete: false` honestly instead of presenting reviewer counts as complete. With zero reviewers, `all([])` is `True`, so a PR with no reviewers reports `reviewer_mapping_complete: true` — the unmapped→false rule holds only when at least one reviewer is unmapped.
  - **Progress (E39 update `{status, note}`, E40 progress-events):** exactly six qualitative states (see §0), member-written note with author/time/version and preserved history, factual task counts only (`total/todo/in_progress/blocked/done`, system-derived, never collapsed into a percent, never used for sorting/ranking). Any eligible Project member may update status/note with If-Match + idempotency + audit + progress event. Archived = frozen/read-only, orphaned = read-only. Dashboard may show status distribution and counts, never an average/total percent. **No percent may appear anywhere in the frontend** — not in a chart, not in a tooltip, not as "progress: 50%". If a legacy mock or design shows a percent, remove it.
- **Requirement:** Resources are files (design docs, implementation plans, figures, images, and similar). File bytes go to S3; basic information and metadata go to MySQL. The frontend must obtain files only through the backend Team Work service, after a permission check, and must never expose a bucket name, a permanent S3 URL, or a raw S3 key to the user, and must never upload directly to S3 with a long-lived credential. The PR list is a mirror for review only: GitHub/Stash is the source of truth, and the frontend must not offer to create, merge, or close a PR from Team Work. Progress is qualitative and member-updated, not derived and not a percent.
- **Acceptance:** A member can list, upload, download, and (where their role allows) archive a resource, can see its name, type, size, version (`entity_version` for archive/delete — see §3.4), uploader, and updated time, and can open a PR from the list in its source system. A non-member cannot obtain a resource or a PR list for a Project they are not in. A large-file upload (multipart, checksummed) completes through the phase loop in §3.8 without the frontend assembling data in Lambda. A download is fetched immediately and its bearer nature is stated honestly.

### 3.9 Decisions and open questions (Context items)

### 3.10 Permissions, errors, and states — no dead flows

- **Backend contract (as implemented) — see also §7:**
  - **Error envelope (every failure):** `{error: {code, message, request_id, current?}}` plus `Cache-Control: no-store`. Team Work 422s use this envelope; FastAPI's own 422s are **remapped to the same envelope** (`VALIDATION_ERROR`) in `main.py` — the `{detail: […]}` shape is unreachable in this app as coded (parsing both remains harmless). `500 INTERNAL_ERROR` fires both on response-schema-validation failure **and** on any unhandled exception (i.e. a server bug) — the UI must report it as a server bug to be reported, not as a user error.
  - **404 vs 403 discipline:** non-member project → `PROJECT_NOT_FOUND` **404** (never a tombstone, never an existence leak); non-Team / unknown team → `TEAM_ACCESS_DENIED` **403**; member-internal failures (non-author comment edit, non-creator transfer, non-driver task patch) → `FORBIDDEN` 403 (safe because the requester is already a member). Two "not found" codes exist, `NOT_FOUND` vs `PROJECT_NOT_FOUND`, both 404 — handle both. SubProject member operations → `INHERITED_MEMBERSHIP` **409** (carrying `current.members_href`; add/remove 403 to non-creators) — follow `members_href` where present, never call member endpoints on a SubProject id expecting an editable roster. System Admin has **no bypass anywhere in Team Work code** (profile "I02 no bypass") — except the orphan-transfer rule, where a Team Admin (not a global admin by virtue of global role alone) may transfer an orphaned Project via E05 — this supersedes the v2 §5 matrix's System-Admin column; the frontend must not show a System Admin action as available in Team Work on the basis of the old matrix alone, and must record the supersession in its proposal.
  - **Version / idempotency / cursor rules:** see §7.2–§7.4. In short: every non-GET handler requires a canonical UUIDv4 `Idempotency-Key` (a human-readable key like `abc-123` fails 422); entity `If-Match` is a quoted integer, Context `If-Match` is a 64-hex hash; on `INVALID_CURSOR` 422, restart that traversal from page one, never surface it as fatal, never persist a cursor across sessions as if stable; on `VERSION_CONFLICT` / `CONTEXT_CHANGED`, show current data and ask the user to re-apply, preserving the draft.
  - **Delete replay (P0-7, corrected):** after an uncertain DELETE response, retrying with the same key returns 204 for every delete type **except project delete**: E31 returns 404 because `_authorize` re-checks the deleted root (`PROJECT_NOT_FOUND`) before the replay lookup (deletes have `_reference` kind `"none"`, which returns 204 on replay). A 404 on replay of any other delete therefore means something else (enclosing project gone or authorization lost), not success. GPT's fix item (short-circuit deletes to the stored 204 ref) is moot for non-project deletes in the delivery and remains open only for E31.
  - **Preflight ordering (corrected — the leak does not occur in the delivery):** `execution.py:_preflight` authorizes first (`require_project` READ / `require_team`) before parsing body mentions, so a non-member submitting a malformed mention gets `PROJECT_NOT_FOUND` 404, not 422. Error precedence is correct here. The frontend must not rely on error precedence to infer existence — it must treat 422-on-mention as a validation error, not as proof of access.
- **Requirement:** Every action must show its permission state honestly. If the user cannot use an action, they must understand why (not signed in, backend unreachable, Team Work not enabled, storage not configured, PR sync not configured, not a Project member, not the creator, orphaned/archived, or a backend error), and must not be led into a form or flow that cannot succeed. Errors from the backend must be shown in the user's language, at the field or action where they occurred, not as a generic failure.
- **Acceptance:** A user can tell, before clicking, whether an action will work for them, and after a failure can tell what happened and what to do next (retry, contact an admin, re-apply a change, clear a filter, cancel and restart a conversion). A revoked Project (creator removed the user, previously cached) is shown as inaccessible with only its cached identification, no fresh Project data, and a way to clear it from the user's list locally; a Project the user never fetched is never revealed; a failed fetch is shown as unreachable, not as revocation. A re-added Project restores access on the next fetch (new epoch — the frontend must re-fetch, not assume the old cache is still valid). A cursor reused after removal yields `INVALID_CURSOR` 422 — the frontend must treat it as "refresh the list", not "revoke all".
- **What you decide:** how permission states, errors, and the revoked/unreachable/not-configured/not-enabled states are presented. The distinctions above are fixed; the presentation is yours.

### 7.2 Pagination and cursors

- Team Work GETs take `cursor` + `limit` (`limit ≥ 1`; the delivered OpenAPI/design state no numeric default — always pass `limit` explicitly). Any query key not in the endpoint's allowlist, or any duplicated key, fails `VALIDATION_ERROR` 422. Booleans must be literal `"true"/"false"`; IDs are integers ≤ 2^53−1.
- Every page is capped at 1 MiB (`TARGET_BYTES`); a short page with `has_more: true` is normal — loop on `has_more` + `next_cursor`, never stop at a short page.
- Cursors are HMAC-signed with the identity secret ("Vegent TeamWork cursor signing v1"); rotation invalidates every stored cursor (5-minute secret cache can mix old/new validity across Lambdas). Every list scope binds route/filter (and actor where the route is actor-scoped; the delivered docs do not enumerate a per-scope actor table — do not rely on one). Scope mismatch still yields `INVALID_CURSOR` 422, and authorization precedes paging (comments scope includes the filter dict; PR scope includes actor except in Context where `shared=True` sets actor `None`; Context section cursors are double-wrapped: outer `context_section` scope bound to the context hash + inner list cursor). On `INVALID_CURSOR` 422: restart that traversal from page one; never surface it as fatal; never pass Context-manifest cursors to standalone list endpoints; never persist a cursor across sessions as if stable.
- Identity lists use `page` (≥1, default 1) + `limit` (1–100, default 20) with response `{items, total, page, limit}`. Team Work lists return `{items, next_cursor, has_more, href}` or `{items, next_cursor, has_more, projection_version}` — read the shape from the endpoint's schema, do not assume an identity-style envelope.

### 7.3 Errors — envelope and codes (build against this plus the delivered OpenAPI and FRONTEND_API_CONTRACT)

- Envelope (every Team Work failure): `{error: {code, message, request_id, current?}}` + `Cache-Control: no-store`. FastAPI's own 422s are remapped to the same envelope (`VALIDATION_ERROR`) in `main.py` — the `{detail: […]}` shape is unreachable in this app as coded (parsing both remains harmless).
- Codes to handle (status in parentheses; error `message` is a string in the envelope; the delivered docs do not fix a constant message string, so key all UI decisions on `code`, never on message text): `PROJECT_NOT_FOUND` (404, non-member project — never a tombstone); `TEAM_ACCESS_DENIED` (403, non-Team/unknown team); `FORBIDDEN` (403, member-internal); `INHERITED_MEMBERSHIP` (409, SubProject member ops — carries `current.members_href` per the delivered OpenAPI 409 description and feedback response P1-9, which states child member/transfer actions consistently include it; follow `members_href` wherever present, and fall back to `ProjectDetail.sections.members` (root URL) if absent. Add/remove on a SubProject return 403 to non-creators; transfer always 409 on a SubProject); `NOT_FOUND` (404, the other "not found" code — handle both); `INVALID_TOKEN` (401, token/user mismatch in `require_team` — the only 401); `VERSION_CONFLICT` (409, stale quoted-integer version, `current` shapes: `{version}`, `{entity_version}`, full ProjectDetail, Task view, Comment view, or progress object); `CONTEXT_CHANGED` (409, stale 64-hex context hash, **no** `current` payload); `INVALID_VERSION` (422, malformed/missing If-Match) vs `VERSION_CONFLICT` (409, stale — a good split, preserve it in UI copy); `INVALID_CURSOR` (422, restart traversal); `INVALID_FILTER` (422, unknown/retired/invisible category filter — not 404); `INVALID_MENTION` (422, whole comment rejected, safe message, no input echo); `CONFIRMATION_REQUIRED` (422, delete without `{"confirm": true}` — note: version is checked **before** confirmation, so stale-version + missing-confirm yields `VERSION_CONFLICT` first); `IDEMPOTENCY_CONFLICT` (409, same key with different body/query/version — including PR sync looping with the same key); `CONVERSION_NOT_READY` (409); `CONVERSION_STATE_CONFLICT` (409, seal/commit from a wrong state); ### 7.4 Headers and bodies — the matrix that must not be unified

- **Replay semantics are "current response", not "original response"** (design §1043 vs v2 §6 — GPT must reconcile this in writing; until then, the frontend must not promise a user that a retry returns exactly what the first attempt returned). Exceptions the frontend must know: E61 prepare replay returns the **stored first-call** `prepared` count (a fresh prepare on an already-`ready` session legitimately returns `prepared: 0` — a real zero, not a fabrication); E03 add-then-remove replay yields 404 instead of the original 201; PR-sync replay returns the **stored snapshot verbatim**, including its stored `project_version` (not the current one — the old 'mixed snapshot' claim was wrong).
- **`If-Match` formats differ by endpoint:** entity version = quoted integer `"123"`; Context version = 64-hex hash, quotes optional. Read the version base from the right field per endpoint: project/task/comment/category version; **root project version** for member add/remove/transfer; **`entity_version`, not `version`**, for resource archive/delete. `current` payload shapes on 409 vary (`{version}`, `{entity_version}`, full ProjectDetail, Task view, Comment view, progress object) — read them, do not assume one shape. E27's version is the **parent** project's version. Version is checked **before** confirmation on deletes, so stale-version + missing-confirm yields `VERSION_CONFLICT` first. Identity non-GET routes do **not** require Idempotency-Key — §7.4's 'every non-GET handler' is true only inside Team Work. All Team Work DTOs forbid extra fields (`additionalProperties: false`), except `ConversionItem.payload`, which is a free-form object.
- **Empty-body POSTs require `{}`:** E16 commit, E29/E30 archive/unarchive, E36/E37 task archive/unarchive, E49/E50 resource archive/unarchive, E60 seal, E61 prepare — send `{}`, not a bare no-body POST, else 422.
- **Delete bodies split two ways — do not unify:** project E31, category E24, task E38, resource E51, context-item E56 require `{"confirm": true}` (else `CONFIRMATION_REQUIRED` 422); member E04 and comment E10 take **no body at all**. A uniform delete helper fails half the deletes.
- **All request DTOs forbid extra fields** (`extra="forbid"`). Sending an invented field (for example, a `team_id` in a body where the team is the path, or a mentions array in a comment create) returns 422. Send exactly the fields in the endpoint's schema.

### 7.5 TextRef, long fields, and Context traversal

- See §3.4: >2,048 chars → TextRef object; resolve via E58 with `If-Match` = context version, character `offset` paging, per-fragment **cap** 131,072 chars — the delivered OpenAPI/contract state no numeric default for E58 `limit`, so **pass `limit` explicitly** — plus `next_offset`/`complete`. `resource_version` is required for kind=resource and forbidden otherwise; missing/malformed Context If-Match on section/E58 fetches → 422 `INVALID_VERSION`. Unicode offsets are character-based (MySQL `CHAR_LENGTH`/`SUBSTRING`), DTO rejects lone surrogates, NFC normalisation applied — the frontend must use character offsets, not byte offsets, for fragments.
- Context traversal rule: manifest first (E11, `If-None-Match` → 304 only with no section/cursor), then each of the 10 sections with its own cursor to `has_more: false`, then all TextRefs for the recorded version. Never record an import receipt, never claim a Context is complete, and never render a Project detail as complete, after only first pages.
